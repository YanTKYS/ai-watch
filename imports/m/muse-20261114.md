## 1. エージェントの仕事は、「考えるモデル」と「実行するモデル」を使い分ける型にする

- 分野: 開発
- 何を楽にするのか: エージェントの全工程を重い推論モデルに任せると、日常の定型作業まで遅く高くつく問題を減らす。
- 再現の仕組み: Google の Gemini 4 Hydrogen（2026-11-12発表）の型を参考にする。Hydrogen は日常のコーディングとエージェントワークフロー向けの高速・効率モデルで、Artificial Analysis Intelligence Index では既定の設定で 51（最高設定では 54）と Argon（50）を上回るとされ、Gemini 3.8 Flash の 2.5 倍の速さで仕事を終えるとされる。料金は入出力 100 万トークンあたり 1.50 ドル／7.50 ドルで、100 万トークンの文脈全体で一律とされる。運用の型としては、難しい推論は Carbon・Argon、日常の実行は Hydrogen と役割を固定し、Antigravity Orchestrator のようにセッション内で自動で切り替える段を入れる。どの仕事をどちらに振るかの基準表を残しておく。
- 何が新しくなったか: モデル選びが「1つのモデルで全部」から、「推論用と実行用の使い分け」へ進んだ。Hydrogen は Gemini アプリ・Google 検索・API・AI Studio など全層で使えるとされ、無料層にも広がった。ただし Antigravity での Orchestrator 利用は有料の Pro・Ultra 向けとされるため、Plus のままでは使えない点に注意する。ベンチマークの数値は Google 自身の発表によるもので、自分の仕事での実測は別に確かめる。
- 出典: https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-hydrogen/?ref=thehype.news

## 2. 脆弱性の対応は、「見つける」と「直す」をエージェントの往復にする型にする

- 分野: セキュリティ・開発
- 何を楽にするのか: 脆弱性の発見と修正が別々の担当・別々の道具に分かれ、見つかったまま直らない期間が長くなる問題を減らす。
- 再現の仕組み: OpenAI の Daybreak Red Team と Daybreak Defense Factory（2026-11-12発表）の型を参考にする。Red Team は複数のエージェントが Web アプリのソースコードと周辺の文脈を読み、攻撃の筋道を探して、報告された脆弱性が本当に突けるものかを確かめる。Defense Factory はその結果や既存の検出ツール（Wiz・Snyk・Endor Labs）からの指摘を受け取り、原因をコードの中でたどって、テスト付きの修正案をマージできる形のプルリクエストとして用意する。運用の型としては、試す範囲をあらかじめ決めた隔離環境で動かし、修正は人が証拠を確認してからマージする関所を必ず挟む。なお Red Team は早期アクセス（申請制）、Defense Factory は Daybreak 利用者向けのプレビューで、料金は未発表とされる。
- 何が新しくなったか: セキュリティ対応が「人が指摘を受け取って直す」形から、「エージェントが見つけて確かめ、修正案まで用意する往復」へ進んだ。修正案は人の承認を経てから本番に入る設計で、自動で直す仕組みではない。
- 出典: https://www.aiaffairs.com/technology/openai-daybreak-red-team-defense-factory-security-tools/

## 3. 研修の教材は、「講師が話すだけ」で遊べるシミュレーションにする型にする

- 分野: 教育・研修
- 何を楽にするのか: 研修の教材作りで、講師の話をスライドや演習に起こし直す手間を省き、受講者が試行錯誤できる教材を短時間で用意する。
- 再現の仕組み: Wharton Generative AI Lab の Primer（2026-11-13公開）の型を参考にする。教師がレッスンを話すと、教育原理に基づいた遊べる（プレイアブルな）シミュレーションをエージェントが生成する。論文・プロンプト・コードがオープンで公開されている。運用の型としては、教材の作り方を「講師の話し言葉→教育原理に沿ったシミュレーション」という固定の流れにし、生成のプロンプトと評価の基準を共有の資産として残す。教材のねらいと試す場面は講師が決め、生成には任せない。
- 何が新しくなったか: 教材作りが「講師が資料を作る」形から、「話すだけで試せるシミュレーションが生成される」形へ進んだ。作り方そのものがオープンで公開され、社内研修への転用を検証しやすくなった。
- 出典: https://x.com/emollick/status/2121001056637431873

## 4. 常駐エージェントの採用は、「性能」ではなく「介入の仕方と費用」で選ぶ型にする

- 分野: 開発・評価
- 何を楽にするのか: 常時稼働するエージェントのモデル選びで、性能の数字だけを見て、不要な介入や費用の膨らみを見落とす問題を減らす。
- 再現の仕組み: Deepnote の Agent Initiative Benchmark（2026-11-13公開）の型を参考にする。現実的な職場の仕事を想定し、12 のフロンティアモデルを合成企業の Slack 環境で評価した。結果では OpenAI の Sol 6.1 などが高コストのモデルを上回り、費用対効果と不要な介入の問題が指摘された。運用の型としては、エージェントの採用前に「自分で動くべき場面・声をかけるべき場面・黙るべき場面」の基準を決め、性能・費用・応答性の 3 つで測る。評価は 1 回の出来ではなく、介入の回数と費用も一緒に記録する。
- 何が新しくなったか: エージェントの評価が「ベンチマークの点数」から、「職場の文脈でいつ動くか・いくらかかるか」まで見る形へ進んだ。高いモデルが必ずしも常駐に向くわけではないことが、定量的に示された。
- 出典: https://x.com/jakubjurovych/status/2121256499552915586

## 5. AI の導入は、「実績のある型」を店頭から選ぶ型にする

- 分野: 法務・営業
- 何を楽にするのか: AI の導入で、1 業務ずつ実証を回して時間がかかる状態をやめ、実績のある型をそのまま持ち込めるようにする。
- 再現の仕組み: Insight の Agent Store（2026-11-12に世界展開）の型を参考にする。実績のある AI 解決策をそろえたオンラインの店頭で、15 のエージェント型を 14 か国で提供するとされる。例として、見積もり助言（Quote Advisor）、秘密保持契約の点検（NDA Review Agent）、部品注文の支援（Parts Order Assist）が挙げられている。導入は数日〜数週間で回すとされ、導入支援と変革管理（AI Flight Academy）や利用費の管理（TokenScope）も同じ店頭に並ぶ。運用の型としては、導入の前に「どの業務に・どの型を・何をもって成功とするか」を一覧にし、型の実績と自社の条件を突き合わせて選ぶ。なお売上・価格・顧客数の数字は発表されていないため、導入の判断は自社の試用で確かめる。
- 何が新しくなったか: AI の導入が「1 業務ずつの実証」から、「実績のある型を店頭で選ぶ」形へ進んだ。契約書の点検や見積もりといった、定型の業務から持ち込める型がそろい始めた。
- 出典: https://techintelpro.com/news/enterprise-tech/digital-transformation/insight-launches-agent-store-to-accelerate-enterprise-ai-adoption

## 6. 顧客対応の長い仕事は、「数日〜数週間かけてゴールを追う」型にする

- 分野: サポート
- 何を楽にするのか: 顧客対応で、1 回の問い合わせへの返信はできても、数日にわたる解決の全体を誰も追わなくなる問題を減らす。
- 再現の仕組み: Decagon の Missions（2026-11-12発表）の型を参考にする。システム・担当者・期間をまたいでゴールを調整する、長期のオーケストレーション機能で、数日〜数週間の仕事を追う。Agent Operating Procedure の枠組みの上に乗り、Duet Autopilot とも連携する。運用の型としては、長い仕事を「ゴール・関わるシステム・関わる人・期限」の 4 つで固定し、進み具合の確認と人への声かけのタイミングをあらかじめ決めておく。途中の判断と結果の結びつきも記録し、あとから振り返れるようにする。
- 何が新しくなったか: 顧客対応のエージェントが「その場の返信」から、「数日かけてゴールまで追う」形へ進んだ。長い仕事の進め方が、製品の機能として組み込まれた。
- 出典: https://futurumgroup.com/insights/decagon-missions-can-purpose-built-orchestration-win-enterprise-cx/

## 7. セキュリティ監査は、「見つけた担当とは別のエージェントが反証する」型にする

- 分野: 開発・セキュリティ
- 何を楽にするのか: AI によるコード監査で、誤検知が多く「本当に問題か」を人が 1 件ずつ確かめ直す手間を減らす。
- 再現の仕組み: Cloudflare の security-audit-skill（GitHub 公開、今週のトレンドで最大の伸び）の型を参考にする。監査は 6 段階で進む。偵察、網羅的な探索、候補の検証、構造化、独立した再検証、報告で、見つけた担当とは別のエージェントが検証（反証を試みる）する点が特徴。結果は機械で読める JSON と報告書で出力される。運用の型としては、監査の手順をこの 6 段階のスキルとして残し、対象コードは外部通信を遮断した隔離環境で動かす。README によると 1 回の実行で見つかるのは繰り返し実行した場合の約半分とされるため、1 回の結果で「問題なし」とは判断せず、正式な脆弱性診断の代わりにはしない。
- 何が新しくなったか: AI 監査が「1 回の生成で指摘を出す」形から、「別のエージェントが反証して絞り込む」多段階の型へ進んだ。監査の手順そのものが再利用できるスキルとして公開された。
- 出典: https://github.com/cloudflare/security-audit-skill

## 8. API のない業務システムは、「画面ではなく構造を読ませる」型で自動化する

- 分野: 事務・現場
- 何を楽にするのか: API のない既存の業務システムへの転記作業を、画面のレイアウトが変わるたびに壊れる従来の RPA から、画面の変化に強い自動化へ変える。
- 再現の仕組み: vercel-labs/agent-desktop（v1.3.0、2026-11-12公開）の型を参考にする。スクリーンショットの画像認識ではなく、OS のアクセシビリティ情報（ボタンや入力欄の構造）を JSON で読み取り、AI エージェントがクリックや入力を行う。ツール自体に AI モデルは含まれず、判断はつないだエージェント側が行う。v1.3.0 では隔離環境で動かす sandbox コマンドが追加された。運用の型としては、操作の手順を「どの構造を・どう操作するか」の一覧として残し、画面の内容やクリップボードのログに個人情報が含まれる可能性があるため、保存先と保存期間をあらかじめ定める。住民情報を扱う端末では外部の AI モデルとつながない線引きも固定する。
- 何が新しくなったか: 業務自動化が「画面の画像を見て操作する」形から、「構造を読んで操作する」形へ進んだ。画面のレイアウトが変わっても動きやすく、隔離実行の段も加わった。
- 出典: https://github.com/vercel-labs/agent-desktop

## 9. 紙の帳票は、「画像も読めるオープンモデル」で項目を JSON にする型にする

- 分野: 経理・事務
- 何を楽にするのか: 紙の申請書や届出書の読み取りで、AI-OCR サービスへの外部送信が難しい帳票を、閉じた環境で処理できるようにする。
- 再現の仕組み: QwenLM/Qwen3-VL（Apache-2.0）の型を参考にする。画像・動画・文書を読み取れるマルチモーダルモデルで、OCR は 32 言語に対応し、暗い・ぼやけた・傾いた画像や、難しい漢字・専門用語にも強くなったとされる。長い文書のレイアウト解析も改善されている。2B〜8B の規模なら一般的な GPU 搭載 PC でも検討できる。運用の型としては、読み取る項目（氏名・住所・申請日など）を JSON の型として固定し、抽出結果は必ず人が最終確認する。過去の紙文書を PDF 化した資料からレイアウトを保ったままテキストを抽出し、RAGFlow などの検索対象に回す流れも作れる。なお日本語の手書き文字や旧字体の精度は、実際の帳票で検証する必要がある。
- 何が新しくなったか: 帳票処理が「外部サービスへ送る」形から、「閉域で動くオープンモデルで項目を JSON にする」形へ進んだ。文書解析の実装例（cookbook）も公開され、試作の段取りが整った。
- 出典: https://github.com/QwenLM/Qwen3-VL

## 10. 社内データへの質問は、「意味の層」を先に作ってから SQL にする型にする

- 分野: 調査・分析
- 何を楽にするのか: 社内の複数のデータベースへの質問で、部署ごとに違う項目の定義（例: 「世帯」の数え方）が食い違い、誤った数字を出す問題を減らす。
- 再現の仕組み: NVIDIA の auto-ontology（Apache-2.0）の型を参考にする。複数のデータベースのメタデータから「どの表に何があり、どの定義が正しいか」という意味の層（オントロジー）を自動で作り、自然言語の質問を SQL に変換して実行し、回答には根拠（どのデータ・定義を使ったか）を付ける。MCP・CLI・API 経由で各種 AI エージェントから使え、ログインと権限管理（RBAC）も備える。運用の型としては、定義の突き合わせを先に済ませて意味の層として残し、質問のたびにその層を通す。既定の設定は NVIDIA のクラウド推論を使うため、閉域で使う場合は推論先を庁内・社内の OpenAI 互換サーバーに変え、個人情報を含む原データには直接接続しない。
- 何が新しくなったか: 社内データへの質問が「モデルに直接 SQL を書かせる」形から、「意味の層で定義をそろえてから SQL にする」形へ進んだ。回答の根拠と権限管理が、分析の土台に組み込まれた。
- 出典: https://github.com/NVIDIA/auto-ontology
