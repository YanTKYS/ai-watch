## 方針と現状

ai-watch の価値は「公式の技術的な更新を、毎日短時間で確認し、後から探せること」にある。静的サイトとPython収集処理の構成を維持し、まず発見しやすさと更新への信頼を改善する。

すでに全期間検索（部分一致・空白区切りAND・NFKC正規化）、日本語IME対応、50件ずつの追加表示、月選択・並び順、最新日の初期展開、OS連動のダークモード、フォーカス表示がある。収集側も選定スコア、不採用理由、公式リリースノートの抜粋、リリース集約、取得失敗時の診断、Brave利用量制限を備える。これらを新機能として再提案しない。

前回以降、期待値による品質回帰チェック、リリース分類とニュース選定の改善、収集状況・鮮度の表示、見出し・通知・キーボード操作の改善が加わった。**前回までの21案は完了8件・一部対応1件・未着手12件**。今回追加する5案を含めると、26案中、完了8件・一部対応1件・未着手17件となる。

## UI/UX・閲覧機能

### F01: カテゴリ・情報源・期間フィルター

- **根拠**: `app.js` の `syncControls()` は検索中に月・並び順を無効化する。`parser.js` の `searchArticles()` は全期間のAND検索のみで、カテゴリ・情報源の専用フィルターがない。
- **提案**: カテゴリ、情報源、取得日の期間を選べるようにする。取得日と公開日は混同しないよう表示する。最初は取得日基準に限定し、条件内はOR・条件間はANDとする。キーワードなしでもフィルターを利用でき、全解除を用意する。収集対象・対象外の説明から既存のF12資料へ辿れるようにする。
- **実装**: 共通の絞り込み状態を持ち、日刊表示と検索表示の適用範囲を明示する。フィード名の重複しない一覧を既存データから作る。URLへの保存はF02と共通化する。
- **受け入れ条件**: 「AIコーディング × Claude Code Releases × 指定期間」で期待した記事だけが出る。0件時は適用中の条件と解除操作が分かり、クリアで元の閲覧状態に戻れる。

### F02: 表示状態と記事への共有URL

- **根拠**: `app.js` でURLから読んでいる状態は `sample` のみ。月・キーワード・並び順は再読み込みで復元されず、記事にページ内の識別子もない。
- **提案**: `?month=2026-10&q=Codex&order=desc` などの条件を共有できるようにする。記事には元URL由来の安定した識別子を設け、指定日の折りたたみを開いて移動する。
- **実装**: `URLSearchParams` / History APIを利用し、`popstate` で戻る・進むに追従する。入力中は `replaceState`、確定操作では必要なときだけ `pushState`。不正な月・条件は安全な既定値へ戻し、`sample` を維持する。検索語がURL・閲覧履歴に残ることをヘルプに示す。
- **受け入れ条件**: URLを別タブで開くと同じ条件と記事を表示する。戻る・進むが機能し、存在しない記事では通常表示と案内へ復帰する。

### F03: 検索結果でもリリース情報を保持

- **状態**: 完了。Issue #10 / PR #11。
- **実装済み**: `search_index.py` → `buildSearchEntries()` で `notes` / `highlights` / `releases` を保持。共通の `renderCard()` で日刊・検索に同じリリース情報を表示し、個別バージョン名も検索対象にした。
- **確認・残課題**: 旧形式・不正URL・安全な文字列描画の回帰テスト、本番/サンプルのインデックス更新がある。種類別の表示や分類精度まで完了したとは扱わず、F09/F17へ引き継ぐ。

### F04: 収集状況・データ鮮度の表示

- **実装済み**: [公開スナップショット](collection-health.md)に実際の試行・完了・最終全成功、フィード別成否と候補/採用件数を保存。公式フィードとインデックス生成を分け、失敗でも前回成功を保つ。全フィード失敗は非0終了し、後続の状態更新・commitを可能な範囲で試みる。秘密値・本文・診断を公開JSONへ入れない。
- **画面と検証**: 正常0件・部分/全失敗・生成失敗・未知を区別し、閲覧時刻から36時間超なら更新遅延とする。記事側の再試行から独立し、sampleは非表示/未取得。保存・互換性・失敗・時刻判定のテストをCIで実行する。

- **実装済み**: 月一覧・日刊・検索の通信/形式不正時にだけ再試行を表示し、条件を保って失敗処理を再実行する。`loadToken` と検索キャッシュを維持し、古い月一覧応答の上書きも防ぐ。
- **確認・残課題**: 通信なしの非同期遷移9シナリオが通常テストから実行される。正常0件・連打・遅い応答・検索解除・追加表示の回帰を保護。F06で通知・待機中のボタン維持・成功後の見出し移動も実装済み。実ブラウザCIはF13、実機評価はF25。

### F06: 見出し・読み上げ・フォーカス改善

- **状態**: 完了（実装）。Issue #23 / PR #24。
- **実装済み**: [閲覧仕様](accessibility.md)に沿って日刊h2→h3→h4→h5、検索h2→h3へ整理。本文へのスキップリンク、別タブの共通説明、検索0件を含む完了通知を追加。最後の追加表示・再試行成功で適切な見出しへ移り、入力欄や選択欄からフォーカスを奪わない。
- **回帰保護**: Node上の12ケースでDOM・通知・フォーカス、debounce/IME中の旧応答、再試行の失敗/成功/離脱、クリア・sample等を検証する。PR #24にはChromiumのキーボード、320px/1280px、実ズーム200%、ライト/ダーク、ARIAツリーの確認報告がある。
- **確認・残課題**: 音声読み上げと実OSのIME確認は未実施であり、ARIA設定のテストと区別する。F25で環境別の検証記録を整える。ブラウザでの手動確認をCIへ継続導入する作業はF13。

### F07: コンパクト表示・日付ナビゲーション

- **根拠**: `style.css` はカードのGrid表示、`renderMonth()` は最新日だけ初期展開する。カード以外の表示形式や日付への移動操作はない。検索は50件単位で追加されるが、日刊は閉じた日を含め全カードのDOMを作る。
- **提案**: タイトルと配信元を中心とするリスト表示を追加し、抜粋は個別に展開する。「すべて開く／閉じる」「日付へ移動」を設ける。日刊の遅延描画は計測で必要になった場合に行う。
- **受け入れ条件**: 表示形式を変えても記事数とリンクが一致し、フィルター条件が保たれる。モバイルで長い英語タイトル・複数抜粋・多数の日付があっても横スクロールが発生しない。

### F08: 既読・あとで読む・関心設定

- **根拠**: 現状は閲覧状態を永続化しないため、毎回すべての記事から確認する必要がある。
- **提案**: 第一段階は端末内の「あとで読む」と明示的な既読操作。元記事URLをキーに `localStorage` へ保存し、関心のあるカテゴリ・情報源を既定条件にできるようにする。閲覧しただけで自動的に非表示にしない。
- **受け入れ条件**: リロード後も状態が残り、全解除・エクスポート・復元ができる。ストレージ無効・容量不足時も閲覧を妨げない。端末間同期がないこと、本番とサンプルの状態が独立していることを明示する。

### F09: 変更種別と破壊的変更の明示

- **根拠**: `selection.py` は変更を `breaking` / `feature` / `change` 等へ分類し、優先順に最大3件を抜粋する。UIは `notes` / `highlights` の文字列表示で、変更種別の専用フィルターはない。
- **提案**: 機械分類であると明示した変更種別バッジと「破壊的変更を含む」フィルターを設ける。表示文言の再解析を避け、集約時の件数・判定不能を構造化してログとインデックスに伝える。判定不能を「影響なし」と見せない。
- **受け入れ条件**: 抜粋に選ばれなかった項目も集計に含まれる。色だけに依存せず、F03で保持済みの個別リンクへ辿れる。旧ログは「種別不明」として読める。追加フィールドは後方互換を保つ。F17で保護した正負例を維持し、未知の内容を「破壊的変更なし」と断定しない。

### F10: RSS/Atomによる購読

- **根拠**: 外部の公式フィードを入力としているが、選定済みの日刊ログを配信するフィードはない。
- **提案**: Markdownを正本として、採用済み記事のタイトル・出典・公開日・取得日・元記事リンクから全体のAtomフィードを生成する。カテゴリ別は需要を見て追加。本文やAI要約は追加しない。

### F26: 検索の一致理由・一致箇所の表示

- **根拠**: `buildSearchEntries()` はタイトル・カテゴリ・配信元・フィード名・抜粋・個別バージョン名を一つの `haystack` にまとめ、`searchArticles()` は一致した記事を返す。どの項目が検索語に一致したかは返さず、UIも通常カードの表示であるため、長い抜粋やバージョン一覧から一致箇所を探す手間が残る。
- **提案**: 第一段階は「主な変更に一致」「リリース名に一致」等、実際に一致した項目を簡潔に示す。必要なら原文の該当箇所を短く表示・強調し、検索語が複数の項目にまたがるAND検索でも理由を説明できるようにする。外部本文取得やAIによる要約は追加しない。
- **依存・境界**: F01は絞り込み、F16は表記揺れの補助、F26は既存検索で一致した根拠の提示。順位付けや採否、検索対象フィールドを変更しない。NFKC正規化後の位置を原文の文字位置として誤用せず、対応付けが難しければ項目名だけの案内に留める。
- **受け入れ条件**: 全角英数・半角カナ・結合文字・複数語AND・個別バージョン名・HTML風の文字列でも一致理由が正しい。DOMはテキストノードと安全な要素で構築し、色だけに頼らず、読み上げを同じ語の過剰な繰り返しにしない。結果件数・順序・50件追加・元リンクが現行と一致し、旧インデックスでも使える。
