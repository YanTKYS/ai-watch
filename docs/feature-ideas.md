# ai-watch 改善提案

作成日: 2026-10-24（JST）

調査基準: `f2487e4`。ソースコード・README・設定・既存テスト・Actions定義を確認した提案。実装済み機能と追加案を分け、今後のIssue化・実装判断に使う。

## 方針と現状

ai-watch の価値は「公式の技術的な更新を、毎日短時間で確認し、後から探せること」にある。静的サイトとPython収集処理の構成を維持し、まず発見しやすさと更新への信頼を改善する。

すでに全期間検索（部分一致・空白区切りAND・NFKC正規化）、日本語IME対応、50件ずつの追加表示、月選択・並び順、最新日の初期展開、OS連動のダークモード、フォーカス表示がある。収集側も選定スコア、不採用理由、公式リリースノートの抜粋、リリース集約、取得失敗時の診断、Brave利用量制限を備える。これらを新機能として再提案しない。

## UI/UX・閲覧機能

### F01: カテゴリ・情報源・期間フィルター

- **根拠**: `app.js` の `syncControls()` は検索中に月・並び順を無効化する。`parser.js` の `searchArticles()` は全期間のAND検索のみで、カテゴリ・情報源の専用フィルターがない。
- **提案**: カテゴリ、情報源、取得日の期間を選べるようにする。取得日と公開日は混同しないよう表示する。最初は取得日基準に限定し、条件内はOR・条件間はANDとする。キーワードなしでもフィルターを利用でき、全解除を用意する。
- **実装**: 共通の絞り込み状態を持ち、日刊表示と検索表示の適用範囲を明示する。フィード名の重複しない一覧を既存データから作る。URLへの保存はF02と共通化する。
- **受け入れ条件**: 「AIコーディング × Claude Code Releases × 指定期間」で期待した記事だけが出る。0件時は適用中の条件と解除操作が分かり、クリアで元の閲覧状態に戻れる。

### F02: 表示状態と記事への共有URL

- **根拠**: `app.js` でURLから読んでいる状態は `sample` のみ。月・キーワード・並び順は再読み込みで復元されず、記事にページ内の識別子もない。
- **提案**: `?month=2026-10&q=Codex&order=desc` などの条件を共有できるようにする。記事には元URL由来の安定した識別子を設け、指定日の折りたたみを開いて移動する。
- **実装**: `URLSearchParams` / History APIを利用し、`popstate` で戻る・進むに追従する。入力中は `replaceState`、確定操作では必要なときだけ `pushState`。不正な月・条件は安全な既定値へ戻し、`sample` を維持する。検索語がURL・閲覧履歴に残ることをヘルプに示す。
- **受け入れ条件**: URLを別タブで開くと同じ条件と記事を表示する。戻る・進むが機能し、存在しない記事では通常表示と案内へ復帰する。

### F03: 検索結果でもリリース情報を保持

- **根拠**: `collect.py` は `Notes` と複数の `Release` をログへ保存し、`app.js` の `renderCard()` はそれらを描画する。一方、`search_index.py` の `parse_log()` と `parser.js` の `buildSearchEntries()` は `highlights` のみ引き継ぐため、検索結果では項目数・個別リリースリンクが失われる。
- **提案**: インデックスとクライアントの検索用記事に `notes` / `releases` を追加し、日刊と検索で同じ情報を表示する。個別バージョン名も検索対象にして、抜粋にないバージョンから探せるようにする。
- **受け入れ条件**: 複数リリースをまとめた記事を検索すると、日刊表示と同じ個別リンクが出る。旧形式のインデックスも読め、不正なリンクは描画しない。本番・サンプルのインデックスとテストを同時に更新する。

### F04: 収集状況・データ鮮度の表示

- **根拠**: UIの「最新」は月内の最新記事日で、最終収集成功日ではない。`collect.py` は記事があるときだけ日刊ログを書き、部分失敗は警告で続行する。`collect.yml` のインデックス生成も失敗を許容するため、記事表示だけでは更新停止や検索データの遅れを判別できない。
- **提案**: `data/collection-status.json`（仮）へ最終試行・最終全フィード成功・フィード別成功/失敗・採用件数を保存し、ヘッダーに「正常／一部取得失敗／更新遅延」を表示する。検索インデックスの生成結果も分ける。取得成功かつ採用0件なら「新着なし」と表示する。
- **実装上の注意**: 全失敗時にも状態を残す。Actions側の追加ファイルの保存対象も変更する。スケジュールの遅延を見込み、遅延判定の閾値は設定可能にする。状態ファイルが古い場合は収集処理が起動しなかった可能性も伝える。公開状態には本文・秘密値・診断用の生レスポンスを含めない。
- **受け入れ条件**: 正常0件、1フィード失敗、全失敗、インデックス生成失敗、スケジュール停止を別々に検証し、過去記事を読み続けられる。時刻はタイムゾーンを明示する。

### F05: 読み込み失敗からの再試行

- **根拠**: `loadMonths()` / `showMonth()` は取得失敗時にメッセージを表示するだけ。検索取得は再入力で再試行できるが、同じ検索語の再適用は `applySearch()` で省略される。
- **提案**: 月一覧・日刊ログ・検索インデックスそれぞれに明示的な「再試行」を付け、表示中の月・条件を保つ。エラー種別と操作を短く案内する。
- **受け入れ条件**: 最初のリクエストだけ失敗する状況から、同じ条件のまま再試行して復帰できる。連打や月変更で遅い古い応答が現在の表示を上書きしない（既存の `loadToken` を維持）。

### F06: 見出し・読み上げ・フォーカス改善

- **根拠**: `index.html` に `role="status"` と `aria-live`、CSSにフォーカス表示はある。一方、検索結果のカード見出しは `h2` の直下でも固定の `h5`、日刊もカテゴリが `h4` 固定。検索完了時はstatusを空にし、件数は別の通常要素に表示する。追加表示の最終ページでは操作中のボタンが非表示になる。
- **提案**: 表示文脈に合わせた見出し階層、検索完了件数の控えめな読み上げ、メインへのスキップリンクを設ける。「さらに表示」後の位置・フォーカスを保ち、最後の追加時にも行き先を失わないようにする。外部リンクが別タブで開くことも分かるようにする。
- **受け入れ条件**: キーボードだけで検索・月切替・折りたたみ・追加表示・クリアを操作できる。読み上げで見出しと完了件数が分かり、入力中の過剰な通知がない。320px幅、200%ズーム、ライト／ダークも実ブラウザで確認する。

### F07: コンパクト表示・日付ナビゲーション

- **根拠**: `style.css` はカードのGrid表示、`renderMonth()` は最新日だけ初期展開する。カード以外の表示形式や日付への移動操作はない。検索は50件単位で追加されるが、日刊は閉じた日を含め全カードのDOMを作る。
- **提案**: タイトルと配信元を中心とするリスト表示を追加し、抜粋は個別に展開する。「すべて開く／閉じる」「日付へ移動」を設ける。日刊の遅延描画は計測で必要になった場合に行う。
- **受け入れ条件**: 表示形式を変えても記事数とリンクが一致し、フィルター条件が保たれる。モバイルで長い英語タイトル・複数抜粋・多数の日付があっても横スクロールが発生しない。

### F08: 既読・あとで読む・関心設定

- **根拠**: 現状は閲覧状態を永続化しないため、毎回すべての記事から確認する必要がある。
- **提案**: 第一段階は端末内の「あとで読む」と明示的な既読操作。元記事URLをキーに `localStorage` へ保存し、関心のあるカテゴリ・情報源を既定条件にできるようにする。閲覧しただけで自動的に非表示にしない。
- **受け入れ条件**: リロード後も状態が残り、全解除・エクスポート・復元ができる。ストレージ無効・容量不足時も閲覧を妨げない。端末間同期がないこと、本番とサンプルの状態が独立していることを明示する。

### F09: 変更種別と破壊的変更の明示

- **根拠**: `selection.py` は変更を `breaking` / `feature` / `change` 等へ分類し、優先順に最大3件を抜粋する。UIは `notes` / `highlights` の文字列表示で、変更種別の専用フィルターはない。
- **提案**: 機械分類であると明示した変更種別バッジと「破壊的変更を含む」フィルターを設ける。表示文言の再解析を避け、集約時の件数・判定不能を構造化してログとインデックスに伝える。判定不能を「影響なし」と見せない。
- **受け入れ条件**: 抜粋に選ばれなかった項目も集計に含まれる。色だけに依存せず、個別の元リリースへ辿れる。旧ログは「種別不明」として読める。必要なデータ形式の移行をF03と調整する。

### F10: RSS/Atomによる購読

- **根拠**: 外部の公式フィードを入力としているが、選定済みの日刊ログを配信するフィードはない。
- **提案**: Markdownを正本として、採用済み記事のタイトル・出典・公開日・取得日・元記事リンクから全体のAtomフィードを生成する。カテゴリ別は需要を見て追加。本文やAI要約は追加しない。
- **受け入れ条件**: 元URLを基に安定したIDを付け、再生成や再実行で既存記事が新規扱いにならない。フィード更新日時と元記事公開日を分け、集約リリースのID方針を決める。XMLエスケープ・絶対URL・件数上限をテストし、Brave検索結果を含めない。

## 収集品質・開発運用

### F11: 選定ルールの事前評価・dry-run

- **根拠**: `--reconsider-excluded` はあるが、`collect.py` のCLIには非書き込みの評価モードがない。`run()` はログ・seen・月一覧を書き換える。既存テストは一時パスと通信の差し替えで安全に評価している。
- **提案**: `--dry-run --skip-brave` と任意の設定・出力先を指定できるCLIを追加する。合成フィクスチャによる旧設定／新設定の採否・カテゴリ・スコア差分を示す。ライブ評価は明示指定にし、フィード本文は保存しない。
- **受け入れ条件**: dry-run前後で既存のログ・dataが不変、Brave呼び出しが0件であることを検証する。`--reconsider-excluded` と組み合わせた結果と書き込み予定を確認できる。既存の通常収集と同じ選定ロジックを通す。

### F12: 情報源の追加判断と品質一覧

- **根拠**: 現在の7フィードは `sources.yml` で管理され、上限は10件。カテゴリにある製品群すべてを専用フィードで追っているわけではなく、Brave検索は記事の保存元にはならない。
- **提案**: 情報源・対象製品・公式性・選定方式・直近成功・採用／除外件数の一覧を作る。追加候補は、公式フィードの有無と利用条件、技術的な情報量、既存ソースとの重複を調べてから採用する。UIには収集対象と対象外も説明する。
- **受け入れ条件**: 設定と一覧が食い違わず、未知形式・gzip・0件・HTML応答をフィクスチャで検証する。新しい配信元のライブ到達性も別途確認する。10件上限の変更は必要性を評価して別途判断する。

### F13: ブラウザE2Eと公開データの契約テスト

- **根拠**: 既存テストはPythonの収集・インデックスとNode上の純粋な検索関数を検証する。HTML/CSS/JSの構造確認もあるが、`app.js` のDOM操作や実際の非同期画面遷移を実ブラウザでは検証していない。
- **提案**: Playwright等で少数の重要シナリオを追加する。`?sample` の50件超のデータを利用し、月切替・検索・IME確定・クリア・追加表示・通信失敗／再試行・遅い応答の競合を検証する。F02以降はURL復元・履歴も追加する。
- **データ検証**: 既存のログとインデックスの一致テストを維持し、F03/F04/F09/F10の新フィールド・後方互換・安全なリンクのテストを追加する。PythonとJSのパーサーには共通の期待データを使う。
- **受け入れ条件**: PR CIで秘密値・外部APIなしに再現し、失敗時にトレースを残せる。デスクトップとモバイル幅を含め、既存の全テストと併用する。テスト用ブラウザ導入に必要な依存関係と実行手順を文書化する。

### F14: 検索データ増加への計測と対策

- **根拠**: 検索インデックスは初回検索時に全件取得し、`buildSearchEntries()` が全件の検索文字列を作る。各入力の検索は全件走査。50件追加表示はDOM数を抑えるが、取得量や走査量は減らさない。
- **提案**: まず1千・1万件の合成データで転送量、初回検索、連続入力の処理時間を計測する。目安として読み込み後の入力から表示までp95で200ms以内を仮目標にし、端末・ブラウザ・測定条件を併記する。超過時にWeb Workerや索引を比較し、必要なら期間別分割を検討する。
- **受け入れ条件**: 最適化前後でAND検索・NFKC・重複排除・並び順が同じ。分割時にも全期間検索の漏れがなく、通信途中の結果を全件と誤表示しない。計測前に現状が遅いとは断定しない。

### F15: 類似ニュースの関連表示

- **根拠**: `count_same_titles()` は異なるURLの同名記事を観測するだけで、統合しない。同じ話題の公式発表とツール更新を比較する導線はない。
- **提案**: まず「関連する可能性がある記事」として併記する。タイトル・製品名・日付などの決定的な規則から始め、URL重複排除とは区別する。元記事を削除したり自動統合したりしない。
- **受け入れ条件**: 同名でも別の変更を誤って隠さず、全記事と元URLが残る。関連付けの理由が分かる。合成の同名／別名／別バージョン事例で誤検出を評価し、有用性が低ければ採用を見送る。

### F16: 日本語の補助・通知連携（条件付き）

- **根拠**: UIは日本語だが公式抜粋は原文のまま。READMEではJev・Geminiの呼び出しや週刊・月刊を現在の対象外にしている。
- **提案**: 低コストな第一歩は用語説明と検索の表記揺れ候補。「要約・翻訳・週刊/月刊ダイジェスト」は別途需要・利用条件・精度・費用を評価する。通知はF10の購読を先行し、必要なら関心カテゴリを選べるメール／Webhook等を検討する。
- **採用条件**: 自動生成の補助文と公式原文を明確に分離し、出典を残す。APIキーをブラウザへ配布しない。通知には明示的な登録・解除・重複防止・秘密値の安全な保管が必要。既定で外部AIや送信サービスを追加しない。

## 実装順序の提案

1. **情報欠落と復帰導線**: F03・F05を小さなPRに分ける。F13の最低限の画面遷移テストを整え、以後の変更を保護する。
2. **探しやすさ**: F01・F02を同じ状態設計で進め、F06のキーボード・読み上げ確認を組み込む。
3. **更新への信頼**: F04を収集・インデックス・UIの一連の変更として実装し、F11で選定調整を安全にする。
4. **継続利用**: F07〜F10・F12を利用者の困りごとに合わせて選ぶ。F09のデータ形式変更はF03と共通設計し、不要な再移行を避ける。
5. **拡張判断**: F14は計測結果、F15・F16は需要と品質評価を条件に着手する。

## 維持する制約と効果の確認

- Markdownログを正本、検索インデックスや配信フィードを再生成可能な派生データとする。旧ログと旧形式の読み取り互換を保つ。
