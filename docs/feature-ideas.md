## 方針と現状

ai-watch の価値は「公式の技術的な更新を、毎日短時間で確認し、後から探せること」にある。静的サイトとPython収集処理の構成を維持し、まず発見しやすさと更新への信頼を改善する。

すでに全期間検索（部分一致・空白区切りAND・NFKC正規化）、日本語IME対応、50件ずつの追加表示、月選択・並び順、最新日の初期展開、OS連動のダークモード、フォーカス表示がある。収集側も選定スコア、不採用理由、公式リリースノートの抜粋、リリース集約、取得失敗時の診断、Brave利用量制限を備える。これらを新機能として再提案しない。

## UI/UX・閲覧機能

### F01: カテゴリ・情報源・期間フィルター

- **根拠**: `app.js` の `syncControls()` は検索中に月・並び順を無効化する。`parser.js` の `searchArticles()` は全期間のAND検索のみで、カテゴリ・情報源の専用フィルターがない。
- **提案**: カテゴリ、情報源、取得日の期間を選べるようにする。取得日と公開日は混同しないよう表示する。最初は取得日基準に限定し、条件内はOR・条件間はANDとする。キーワードなしでもフィルターを利用でき、全解除を用意する。収集対象・対象外の説明から既存のF12資料へ辿れるようにする。
- **実装**: 共通の絞り込み状態を持ち、日刊表示と検索表示の適用範囲を明示する。フィード名の重複しない一覧を既存データから作る。URLへの保存はF02と共通化する。
- **受け入れ条件**: 「AIコーディング × Claude Code Releases × 指定期間」で期待した記事だけが出る。0件時は適用中の条件と解除操作が分かり、クリアで元の閲覧状態に戻れる。

### F02: 表示状態と記事への共有URL

- **根拠**: `app.js` でURLから読んでいる状態は `sample` のみ。月・キーワード・並び順は再読み込みで復元されず、記事にページ内の識別子もない。
- **提案**: `?month=2026-10&q=Codex&order=desc` などの条件を共有できるようにする。記事には元URL由来の安定した識別子を設け、指定日の折りたたみを開いて移動する。
- **実装**: `URLSearchParams` / History APIを利用し、`popstate` で戻る・進むに追従する。入力中は `replaceState`、確定操作では必要なときだけ `pushState`。不正な月・条件は安全な既定値へ戻し、`sample` を維持する。検索語がURL・閲覧履歴に残ることをヘルプに示す。
- **受け入れ条件**: URLを別タブで開くと同じ条件と記事を表示する。戻る・進むが機能し、存在しない記事では通常表示と案内へ復帰する。

### F03: 検索結果でもリリース情報を保持

- **状態**: 完了。Issue #10 / PR #11。
- **実装済み**: `search_index.py` → `buildSearchEntries()` で `notes` / `highlights` / `releases` を保持。共通の `renderCard()` で日刊・検索に同じリリース情報を表示し、個別バージョン名も検索対象にした。
- **確認・残課題**: 旧形式・不正URL・安全な文字列描画の回帰テスト、本番/サンプルのインデックス更新がある。種類別の表示や分類精度まで完了したとは扱わず、F09/F17へ引き継ぐ。

### F04: 収集状況・データ鮮度の表示

- **根拠**: UIの「最新」は月内の最新記事日で、最終収集成功日ではない。`collect.py` は記事があるときだけ日刊ログを書き、部分失敗は警告で続行する。`collect.yml` のインデックス生成も失敗を許容するため、記事表示だけでは更新停止や検索データの遅れを判別できない。
- **提案**: `data/collection-status.json`（仮）へ最終試行・最終全フィード成功・フィード別成功/失敗・採用件数を保存し、ヘッダーに「正常／一部取得失敗／更新遅延」を表示する。検索インデックスの生成結果も分ける。取得成功かつ採用0件なら「新着なし」と表示する。
- **実装上の注意**: 全失敗時にも状態を残す。Actions側の追加ファイルの保存対象も変更する。スケジュールの遅延を見込み、遅延判定の閾値は設定可能にする。状態ファイルが古い場合は収集処理が起動しなかった可能性も伝える。公開状態には本文・秘密値・診断用の生レスポンスを含めない。
- **受け入れ条件**: 正常0件、1フィード失敗、全失敗、インデックス生成失敗、スケジュール停止を別々に検証し、過去記事を読み続けられる。時刻はタイムゾーンを明示する。

### F05: 読み込み失敗からの再試行

- **状態**: 完了。Issue #12 / PR #13。
- **実装済み**: 月一覧・日刊・検索の通信/形式不正時にだけ再試行を表示し、条件を保って失敗処理を再実行する。`loadToken` と検索キャッシュを維持し、古い月一覧応答の上書きも防ぐ。
- **確認・残課題**: 通信なしの非同期遷移9シナリオが通常テストから実行される。正常0件・連打・遅い応答・検索解除・追加表示の回帰を保護。再試行後のフォーカスや読み上げ改善はF06、実ブラウザCIはF13。

### F06: 見出し・読み上げ・フォーカス改善

- **根拠**: `index.html` に `role="status"` と `aria-live`、CSSにフォーカス表示はある。一方、検索結果のカード見出しは `h2` の直下でも固定の `h5`、日刊もカテゴリが `h4` 固定。検索完了時はstatusを空にし、件数は別の通常要素に表示する。追加表示の最終ページでは操作中のボタンが非表示になる。
- **提案**: 表示文脈に合わせた見出し階層、検索完了件数の控えめな読み上げ、メインへのスキップリンクを設ける。「さらに表示」とF05の再試行後の位置・フォーカスを保ち、操作ボタンが消えたときにも行き先を失わないようにする。外部リンクが別タブで開くことも分かるようにする。
- **受け入れ条件**: キーボードだけで検索・月切替・折りたたみ・追加表示・クリアを操作できる。読み上げで見出しと完了件数が分かり、入力中の過剰な通知がない。320px幅、200%ズーム、ライト／ダークも実ブラウザで確認する。

### F07: コンパクト表示・日付ナビゲーション

- **根拠**: `style.css` はカードのGrid表示、`renderMonth()` は最新日だけ初期展開する。カード以外の表示形式や日付への移動操作はない。検索は50件単位で追加されるが、日刊は閉じた日を含め全カードのDOMを作る。
- **提案**: タイトルと配信元を中心とするリスト表示を追加し、抜粋は個別に展開する。「すべて開く／閉じる」「日付へ移動」を設ける。日刊の遅延描画は計測で必要になった場合に行う。
- **受け入れ条件**: 表示形式を変えても記事数とリンクが一致し、フィルター条件が保たれる。モバイルで長い英語タイトル・複数抜粋・多数の日付があっても横スクロールが発生しない。

### F08: 既読・あとで読む・関心設定

- **根拠**: 現状は閲覧状態を永続化しないため、毎回すべての記事から確認する必要がある。
- **提案**: 第一段階は端末内の「あとで読む」と明示的な既読操作。元記事URLをキーに `localStorage` へ保存し、関心のあるカテゴリ・情報源を既定条件にできるようにする。閲覧しただけで自動的に非表示にしない。
- **受け入れ条件**: リロード後も状態が残り、全解除・エクスポート・復元ができる。ストレージ無効・容量不足時も閲覧を妨げない。端末間同期がないこと、本番とサンプルの状態が独立していることを明示する。

### F09: 変更種別と破壊的変更の明示

- **根拠**: `selection.py` は変更を `breaking` / `feature` / `change` 等へ分類し、優先順に最大3件を抜粋する。UIは `notes` / `highlights` の文字列表示で、変更種別の専用フィルターはない。
- **提案**: 機械分類であると明示した変更種別バッジと「破壊的変更を含む」フィルターを設ける。表示文言の再解析を避け、集約時の件数・判定不能を構造化してログとインデックスに伝える。判定不能を「影響なし」と見せない。
- **受け入れ条件**: 抜粋に選ばれなかった項目も集計に含まれる。色だけに依存せず、F03で保持済みの個別リンクへ辿れる。旧ログは「種別不明」として読める。追加フィールドは後方互換を保つ。F17の誤分類例を点検してから強い警告表示を加える。

### F10: RSS/Atomによる購読

- **根拠**: 外部の公式フィードを入力としているが、選定済みの日刊ログを配信するフィードはない。
- **提案**: Markdownを正本として、採用済み記事のタイトル・出典・公開日・取得日・元記事リンクから全体のAtomフィードを生成する。カテゴリ別は需要を見て追加。本文やAI要約は追加しない。
- **受け入れ条件**: 元URLを基に安定したIDを付け、再生成や再実行で既存記事が新規扱いにならない。フィード更新日時と元記事公開日を分け、集約リリースのID方針を決める。XMLエスケープ・絶対URL・件数上限をテストし、Brave検索結果を含めない。

### F13: ブラウザE2Eと公開データの契約テスト

- **状態**: 一部対応。PR #11でカードの共通描画・メタデータ保持・安全なリンク、PR #13で最小DOMとfetchをモックした非同期遷移テストを追加した。`unittest` からNodeテストを実行し、PR CIで動く。これは実ブラウザE2Eとは区別する。
- **残る提案**: 既存の高速なNodeテストを残し、Playwright等で少数の実ブラウザシナリオをCIに追加する。`?sample` の50件超のデータで月切替・IME確定・クリア・追加表示・再試行を検証する。応答順の大量の組み合わせは既存Nodeテストに任せ、E2Eではブラウザ固有のDOM・フォーカス・レイアウトを補完する。F02の実装後はURL復元・履歴も追加する。
- **データ検証**: F03のフィールド保持・後方互換と既存のログ/インデックス一致テストは対応済み。F04/F09/F10で形式を拡張するときに契約テストを追加する。PythonとJSのパーサーには共通の期待データを使う。
- **受け入れ条件**: PR CIで秘密値・外部APIなしに再現し、失敗時にトレースを残せる。デスクトップとモバイル幅を含め、既存の全テストと併用する。テスト用ブラウザ導入に必要な依存関係と実行手順を文書化する。

### F14: 検索データ増加への計測と対策

- **根拠**: 検索インデックスは初回検索時に全件取得し、`buildSearchEntries()` が全件の検索文字列を作る。各入力の検索は全件走査。50件追加表示はDOM数を抑えるが、取得量や走査量は減らさない。
- **提案**: まず1千・1万件の合成データで転送量、初回検索、連続入力の処理時間を計測する。目安として読み込み後の入力から表示までp95で200ms以内を仮目標にし、端末・ブラウザ・測定条件を併記する。超過時にWeb Workerや索引を比較し、必要なら期間別分割を検討する。
- **受け入れ条件**: 最適化前後でAND検索・NFKC・重複排除・並び順が同じ。分割時にも全期間検索の漏れがなく、通信途中の結果を全件と誤表示しない。計測前に現状が遅いとは断定しない。

### F15: 類似ニュースの関連表示

- **根拠**: `count_same_titles()` は異なるURLの同名記事を観測するだけで、統合しない。同じ話題の公式発表とツール更新を比較する導線はない。
- **提案**: まず「関連する可能性がある記事」として併記する。タイトル・製品名・日付などの決定的な規則から始め、URL重複排除とは区別する。元記事を削除したり自動統合したりしない。
- **受け入れ条件**: 同名でも別の変更を誤って隠さず、全記事と元URLが残る。関連付けの理由が分かる。合成の同名／別名／別バージョン事例で誤検出を評価し、有用性が低ければ採用を見送る。

### F16: 日本語の補助・通知連携（条件付き）

- **根拠**: UIは日本語だが公式抜粋は原文のまま。READMEではJev・Geminiの呼び出しや週刊・月刊を現在の対象外にしている。
- **提案**: 低コストな第一歩は用語説明と検索の表記揺れ候補。「要約・翻訳・週刊/月刊ダイジェスト」は別途需要・利用条件・精度・費用を評価する。通知はF10の購読を先行し、必要なら関心カテゴリを選べるメール／Webhook等を検討する。
- **採用条件**: 自動生成の補助文と公式原文を明確に分離し、出典を残す。APIキーをブラウザへ配布しない。通知には明示的な登録・解除・重複防止・秘密値の安全な保管が必要。既定で外部AIや送信サービスを追加しない。

## 棚卸で追加した提案

### F17: 記事選定・リリース分類の品質改善

- **根拠**: F12の品質評価とF11の比較結果では、業界事例・管理ダッシュボードの混入に加え、曖昧な修正文の採用、SDKの `internal: remove …` や `mcp: remove … examples` の破壊的変更扱いが残っている。「Bug fixes and reliability improvements」は保存済みログでは変更扱いだが、現在の合成入力ではother→unknownでも採用される。実フィードの入力と合成例の判定内訳を同一とは扱わない。`selection.py` は一般的な単語・接頭辞で分類しており、内部・サンプルという文脈を常に優先できるとは限らない。
- **提案**: まず既知の定型的な修正文と内部・サンプル変更の分類を小さな変更で改善する。判定不能な内容を一律除外せず、見落とし防止の方針を保つ。ニュース側は新モデル・API・モデル廃止を残し、業界事例や管理用途を抑える設定を別の差分として比較する。F11のデモ用の語や閾値をそのまま本番へ移さない。
- **依存・境界**: F18の明示的な期待値を先に整える。F09は分類結果の見せ方、F17は分類・採否そのものの品質。既存の保存記事の一括削除や再選定は別判断とし、当初は今後の収集にだけ適用する。
- **受け入れ条件**: 曖昧な修正文・CI削除・examples修正の負例と、実際の利用者向けの機能廃止・設定削除の正例を対にして検証する。新モデル・Decisions API・Copilotモデル廃止・Codex機能更新を落とさず、地域変更や技術的な研究記事も追加例で点検する。dry-runと通常収集の共通処理を維持し、改善・悪化・判断保留をPRに示す。

### F18: dry-runの期待値集計と品質回帰検出

- **根拠**: `selection-evaluation.json` の `expectations` はkeep/review/checkという人向けの注記で、`selection_preview.py` の採否・終了コードには使われない。差分9件が出ても、そのうちどれが改善・取りこぼしなのかは現在は人が読んで判断する。
- **提案**: F11の比較出力を再利用して、期待する採用/除外、カテゴリ、リリース分類の一致・不一致を集計する小さな評価モードを追加する。reviewを自動で除外正解に変換せず、期待値と理由を人が確定する。未確定例は「要確認」として別枠に置き、評価の分母から分ける。
- **過適合への対策**: 規則を調整する例と、調整に使わない検証例を分ける。フィードの説明文・HTML形式・否定表現・技術的な導入事例も合成で増やし、特定のタイトルだけを当てる変更を避ける。小さな評価セットの成績を実際のニュース全体の精度とは呼ばない。
- **受け入れ条件**: 現行/変更案それぞれの不一致記事・理由・要確認件数が分かる。固定した重要正例の退行はCIで検出でき、品質判定モードの失敗終了と通常dry-runの処理成功を区別する。通信・書き込みなしを保ち、同じ入力は同じ結果になる。F11のCLIや出力を作り直さない。

### F19: 製品・用途の複数タグ

- **根拠**: `classify()` は `classify_order` で最初に一致した単一カテゴリを返す。たとえばCopilotのモデル廃止は「API・料金・制限」、Python SDKは設定で「MCP・連携技術」固定となり、製品・言語・用途の軸がカテゴリ1つに収まりにくい。
- **提案**: 既存カテゴリを残したまま、製品（Codex/Copilot等）・用途（CLI/API/MCP等）を小さな決定的な規則で複数付与する。最初は既存のタイトル・情報源・抜粋から作る派生データに限定し、本文取得や外部AIは追加しない。確定できないものにタグを推測で埋めない。
- **依存・境界**: F01のフィルター状態と連携するが、最初のF01実装の必須条件にはしない。F15の記事同士の関連付け、F16の表記揺れ補助とは別に、1記事の所属を補う機能とする。
- **受け入れ条件**: 「Copilot × API・料金・制限」のような複数軸で探せる。既存カテゴリ・表示順・元URLを変えず、タグなしの旧データも読める。誤付与・未付与の代表例と、タグ規則を増やす際の維持手順をテスト・文書に残す。

### F20: 長期停止後の取りこぼし確認・復旧手順

- **根拠**: 現在は `max_age_days: 7` とフィード内の採用候補上限があり、`--reconsider-excluded` も現在のフィードに残る対象だけを再評価する。F05は閲覧の再試行なので、収集が長期間止まって記事を逃した場合の復旧手段にはならない。
- **提案**: まずF04の状態記録と組み合わせ、「最後に確認できた期間」「フィードに残る範囲」「復元できない可能性のある範囲」を示す運用手順を整える。日付・候補範囲を明示したdry-run比較を経て、必要な場合だけ限定的な補完収集を行う方式を検討する。
- **依存・境界**: F04は停止の検知と鮮度表示、F20は検知後の対応。フィードから消えた過去記事を復元できると約束しない。別のアーカイブAPIや全サイト巡回、恒常的な期間拡張は前提にせず、取得できる範囲と利用条件が整う場合だけ補完を実装する。
- **受け入れ条件**: 7日を超える停止・候補上限超過・月またぎ・既存URLとの重複を合成データで検証し、既存ログ・履歴を壊さない。元記事公開日と補完取得日を区別し、検索インデックスも再生成可能にする。Braveは補完対象にせず、API利用量を変えない。未回収の期間は不明のまま明示する。

### F21: 同日リリースの順序・代表バージョン検証

- **根拠**: `feeds.parse_date()` は日時をJSTの日付に変換し、`select_entries()` / `choose()` は公開日で安定ソートする。同じ日付ではフィード内の順序が代表リリース・見出し・抜粋の選択に影響する。実際の誤順序を確認したわけではないが、日時の新旧を日付だけから再判定できない。
- **提案**: 同日・順序逆転・同時刻・複数タグ体系のテストを先に用意し、影響を確認する。必要な場合は選定中に元の公開日時を保持して比較し、UIの公開日表示は維持する。文字列順や単純なバージョン番号比較だけで最新と決めない。
- **依存・境界**: F03はリリース情報の保持、F21はその代表と順番への信頼。変更が必要と判明するまではデータ形式の移行や過去ログの書き換えをしない。
- **受け入れ条件**: フィード順が日時順でない例、v1.9/v1.10、SDK本体と別パッケージのタグ混在を扱い、見出し・集約先・抜粋が定めた順序と一致する。日時不明時のフォールバックを明示し、旧データ・dry-runにも互換性を保つ。
