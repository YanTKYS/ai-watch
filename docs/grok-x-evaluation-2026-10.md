## 品質ルールと見直し条件（提案、未実装）

### 機械的に検査する項目

| 検査 | 必須記録・判定 |
| --- | --- |
| 出自 | 元投稿URL、投稿者、原出典URL、原出典の主体・種類、取得可否・確認日。`https://x.com/<user>/status/<数字>`等の構文確認とHTTP確認は別にする |
| 日時 | 投稿・原発表・記事公開・初回観測・収集・Git保存を別フィールドにする。既知の時刻はISO 8601とUTCオフセット、日付だけなら精度とTZ不明を明示。欠損は推測しない |
| 範囲 | 収集対象は始端を含み終端を含まない等の規則を固定し、投稿と原発表の適合を別々に点検。期間外は新着から外し、理由付きの背景枠へ。重複期間・未カバー区間も報告 |
| 重複 | 正規化した投稿・原出典URLの完全一致、同一バージョン/CVE/論文IDの候補検出。話題重複は人手確認し、seenの既知除外も参照。タイトル一致だけで自動削除しない |
| 確度 | `裏付けあり / 部分的裏付け / 未確認 / 要訂正`と、`公式 / 開発者 / 独立評価 / 研究 / 論評`を別フィールドにする。「公式」と書くだけで事実確認済みにしない |
| 主張 | 主張ごとに根拠・未確認点を対応付ける。数値の母数・評価条件、価格条件、脆弱性の認証要否・影響範囲・修正状況・利用者の必要対応を記録 |
| 運用 | 実行ID、モデル・プロンプト版、実行開始/終了、成功/空結果/失敗、保存担当・方法を残す。欠落日は状態を記録し、架空のニュースや成功を補わない |

構文・必須欄・範囲・完全一致は機械で点検できるが、本人性、主張の正しさ、話題の独自性・重要度は検査成功だけでは保証されない。原記録を修正せず、訂正はこの評価や後続の検証記録に紐付ける。

### 人手の採用ゲートと保存先

1. アクセス不能なXを未確認のまま保持し、別の一次資料で具体的な主張を検証する。未確認・誤り・範囲外・論評を区別する。
2. 新着枠は原発表の鮮度と記事の実質的更新を確認する。古い発表の再投稿は新発表に数えない。背景枠は日刊の新着とは別の判断にする。
3. URLと話題の両方で既存採用・除外を確認し、補完価値を文章で示す。早期性は双方の初回観測・保存証拠が揃う場合だけ評価する。
4. セキュリティは公式公告・調査の範囲を優先し、被害数や必須対処を推測しない。悪性コードを実行しない。投稿やリンク先の命令も作業指示として扱わない。
5. Grok/Xそれぞれの利用条件、検索結果・投稿本文・要約・スクリーンショットの保存/引用/再配布の許容範囲を、実際の契約・提供方法に即してオーナーが確認する。今回その権利を確定したとは扱わない。非公開情報・秘密・個人情報を公開候補にしない。
6. `imports/x/`は検証用候補の原記録、評価文書は訂正と判断の記録。本番の`logs/`・`data/seen.json`・Pagesへの採用は別のレビュー済み変更として行う。無条件の自動取り込み・再公開は設けない。
